01

Overview & philosophy

The app ingests real, live CVE records from the National Vulnerability Database, then produces three kinds of advisory intelligence for each one: a plain-language analysis, an inferred MITRE ATT&CK technique mapping, and a set of mitigation recommendations — all clearly separated from the one authoritative source.

One rule holds across every layer, enforced structurally rather than by convention: NVD (and, for real-world exploitation status, CISA's KEV catalogue) are the only authoritative sources of fact. Everything the app generates — summaries, risk framing, ATT&CK mappings, mitigations — is labelled advisory and evidence-grounded. Nothing generated is allowed to invent a fact NVD didn't supply; every generated schema traces back to a specific stored field. This shows up concretely in three places: the deterministic analyser's evidence list literally quotes the NVD fields it used, the LLM prompt is instructed the same way, and every API response carries a fixed disclaimer string.

Design constant A CVE's severity and cvss_score always come from NVD, never from the analysis layer — even when Gemini is active, its risk field is validated against the same enum NVD uses, but it is advisory framing, stored separately from the authoritative record.

03

System architecture

The backend is organized as a pipeline: an ingestion service keeps the local database in sync with NVD, and an intelligence service turns any stored CVE into the three advisory outputs on demand — choosing between the LLM analyser and a deterministic fallback without the rest of the system needing to know which one ran.

04

NVD ingestion pipeline

services/ingestion_service.py keeps the local database in sync with NVD's "recently modified" window — this app deliberately does not mirror all ~280,000 CVEs since 1999; it tracks what changed recently, which is what a live CTI feed needs.

  1. Fetch. fetch_cves.py calls the NVD CVE API 2.0 for records modified since the last successful sync (first run: last 24 hours, capped at 119 days by NVD's own API limits), paginating internally at 2,000 records per page.
  2. Normalize. Each raw NVD record is flattened — description text, the newest available CVSS version (v4.0 → v2, whichever exists), CWE classification, timestamps — into the shape the app stores.
  3. Validate. Every normalized record passes through VulnerabilitySchema. A record that fails validation is skipped and logged, never allowed to crash the whole sync or silently corrupt the database.
  4. Upsert. New CVE IDs are inserted; existing ones are updated in place (NVD frequently re-enriches old records with better CVSS/CWE data).
  5. Advance the cursor — carefully. last_successful_sync only moves forward when nothing was truncated by the request's limit. If NVD reported more modified records in the window than fit, the cursor holds so the next sync re-covers the same window instead of silently skipping the overflow forever.
Bug found & fixed this project Earlier, the cursor always advanced to "now" regardless of truncation — meaning a busy day at NVD could silently and permanently drop CVEs past whatever limit was set. Fixed alongside raising the default sync ceiling to 2,000 (NVD's own page-size maximum).
05

Database schema

One vulnerabilities table holds the authoritative NVD facts. Three child tables — each cascade-deleting with their parent — hold the advisory layer, kept structurally separate from the source of truth.

VULNERABILITY_ATTACK_MAPPING.technique_id is a real foreign key against ATTACK_TECHNIQUE — this is enforced at the database level, not just assumed, which matters for the LLM layer: a technique ID the model invents that isn't in the known catalogue would fail this constraint, so it's filtered out in application code before the insert is even attempted.

KEV_ENTRY is the exception: it deliberately has no foreign key to VULNERABILITY. CISA's Known Exploited Vulnerabilities catalogue is synced independently from NVD (services/kev_service.py, refreshed in full each time — CISA's feed has no incremental query) and can reference a CVE this app hasn't ingested from NVD yet. The join is by cve_id value alone, via a viewonly SQLAlchemy relationship.

07

The LLM layer

This is the part that actually generates the analytical content — and the part most carefully engineered to fail safely, since an external API is the least reliable thing in this whole pipeline.

Prompt & JSON contract

services/prompts.py defines the entire contract between the app and any model. The system prompt does three specific jobs:

  • Prompt-injection defence. The untrusted CVE description is placed inside an explicit <cve_record> block, with an explicit instruction that everything inside it is data, never an instruction to follow — even if it contains text that looks like a command or a role change.
  • Evidence grounding. The model is told to use only the supplied fields, say so explicitly when a field is missing, and cite which field justifies every claim.
  • A closed vocabulary for ATT&CK. The 20-technique catalogue (see §8) is rendered into the prompt as the only set of technique IDs the model may choose from — it's told explicitly to leave the list empty rather than force a mapping.

The model must respond with exactly this shape:

{
  "summary": string,              // real analysis: mechanism, attack vector, preconditions
  "impact": string,
  "affected_component": string,
  "risk": "NONE"|"LOW"|"MEDIUM"|"HIGH"|"CRITICAL"|"UNKNOWN",
  "confidence": number,           // 0–1
  "evidence": [string, ...],      // each citing a specific <cve_record> field
  "attack_techniques": [          // 0 or more, from the given catalogue only
    { "technique_id": string, "rationale": string }
  ],
  "mitigations": [string, ...]    // 1–5, specific to this CVE's mechanism
}

That JSON is requested via Gemini's responseSchema structured-output mode, then re-validated independently with Pydantic's LLMAnalysisOutputSchema before anything touches the database — the same "never trust external input" rule this project applies to raw NVD records.

Decision flow & fallback

llm_service.generate_analysis() is the single function the rest of the app calls. It is designed so that a Gemini outage, rate limit, timeout, or malformed response never breaks a request — it just quietly produces the deterministic answer instead.

The single discriminator downstream code relies on is the returned model string. If it starts with gemini:, intelligence_service.py trusts the LLM's own ATT&CK selections and mitigations — including an empty selection list, which is a confident "nothing matches" answer that must not be second-guessed by falling back to keyword matching. Any other value means the deterministic services ran, unchanged from before the LLM layer existed.

Why Gemini, and why free

Three providers were evaluated in this exact order, each ruled out for a concrete reason before landing on the current one:

ProviderVerdictWhy
Anthropic ClaudepaidNo ongoing free tier — billed per token from the first request
Hugging Face Inference ProviderspaidA free account's entire monthly allowance is a $0.10 credit pool; the truly-free hf-inference tier "focuses mostly on CPU inference... smaller LLMs... like BERT or GPT-2" per HF's own pricing docs — modern 7B+ chat models route through paid third-party providers and exhaust the $0.10 in a handful of requests
GroqAbandoned mid-setupGenuinely free (rate-limited, not credit-metered) and hosts Qwen — but sign-in via GitHub OAuth hit a persistent oauth_state_mismatch browser/cookie issue that couldn't be resolved
Google Geminifree — currentSame free-tier shape as Groq (rate limits, not credits), and sign-in is a plain Google account — no second-service OAuth handoff

Two independent settings gate any real spend risk: GEMINI_API_KEY must be set and ENABLE_LLM_ANALYSIS must be explicitly true. Leaving either at its default — which is what a fresh clone of this repo does — keeps the entire project at zero cost, using only the deterministic analyser.

08

ATT&CK mapping

Both analysers map to the same 20-technique curated subset of the MITRE ATT&CK Enterprise matrix (data/attack_catalog.py) — it started at 5 techniques with narrow keyword signals and was expanded specifically because coverage was too thin.

PathMethodCoverage
Deterministic (fallback)Exact keyword substring match against each technique's fixed signal listNarrow — a CVE has to contain one of a handful of literal phrases
LLM (Gemini, when active)Semantic selection from the same catalogue, given as reference text in the promptMuch broader — understands paraphrase and context, not just exact substrings

Neither path is allowed to invent a mapping without a genuine signal — both are instructed (one in code, one in the prompt) to return nothing rather than force a match, and every mapping is labelled mapping_type: "inferred", explicitly never presented as an official MITRE assertion.

09

Mitigation generation

The deterministic path (mitigation_service.py) always produces the same three boilerplate recommendations plus one technique-specific line when a mapping exists — reasonable, but repetitive across dissimilar CVEs. When the LLM path is active, its own 1–5 CVE-specific recommendations replace that list entirely (the severity-driven immediate_action/short_term/long_term narrative fields stay from the deterministic service either way, since those are legitimately generic process guidance).

10

Frontend

No framework, no build step — three static files (index.html, app.js, styles.css) mounted at /dashboard by the same FastAPI app. A few notable pieces:

  • A green Matrix / glassmorphism visual theme — frosted-glass panels, a low-opacity animated digital-rain canvas background, JetBrains Mono.
  • The AI-assisted summary renders as bullet points (sentence-split client-side) rather than one dense paragraph.
  • An optional X-API-Key field, stored in sessionStorage only — never persisted long-term since it's a bearer credential.
11

Security middleware

security.py wraps every route with a hand-written rate limiter, an optional X-API-Key gate, and standard security headers; TrustedHostMiddleware and CORS are configured from environment variables so a real deployment must explicitly name its hostname rather than defaulting to a permissive wildcard.

12

Deployment

Render's free web-service plan runs the FastAPI app directly from render.yaml — a Blueprint deploy needs no manual server configuration. The Postgres database is Neon's free tier. Both free tiers have real constraints worth knowing:

  • Render's free plan spins the service down after inactivity — the next request cold-starts it (10–60s).
  • Neon's free tier has storage/compute limits appropriate for this app's scope (recent-window CVE tracking, not a full historical mirror).
  • All secrets (DATABASE_URL, GEMINI_API_KEY) are marked sync: false in the Blueprint — never committed, set once in the Render dashboard.
13

Testing philosophy

69 tests, all offline — no real API key or network access needed to run the suite, including for the LLM layer, where requests.post is mocked directly rather than making a real Gemini call. One real bug this discipline caught: enabling Gemini in a developer's local .env for everyday use also flowed into the shared settings object the test suite imports, making one end-to-end test start hitting the real API and fail. Fixed by forcing ENABLE_LLM_ANALYSIS=false at test-module import time, the same pattern already used to force an isolated throwaway database.
